Topic 01 · Foundations

Introduction to SDN

Software Defined Networking (SDN) is a modern approach to building and managing networks where the intelligence (control logic) is separated from the hardware that forwards traffic.

In traditional networks, every router and switch contains its own control logic — making them hard to configure and automate at scale. SDN solves this by moving all control to a central software controller.

Core Idea

🧠 Controller

The brain of the network. Makes all routing and policy decisions centrally.

⚙️ Switches / Routers

The hands. Only forward packets based on rules sent by the controller.

📡 Programmability

The network can be configured via software and APIs — no manual CLI per device.

🔓 Vendor Neutrality

Standard interfaces like OpenFlow allow mixing equipment from different vendors.

        Applications
             |
             v
  +----------------------+
  |    SDN Controller    |   ← Makes all decisions
  +----------------------+
       |       |       |
       v       v       v
    Switch  Switch  Router   ← Forward packets only

Key Principles

  • Separation of control and data planes — control logic lives in the controller, not in each device
  • Centralized intelligence — one controller maintains a global view of the entire network
  • Programmability — network behavior configured via software and APIs
  • Vendor neutrality — standard southbound interfaces allow multi-vendor interoperability
Topic 02 · Foundations

Overview & Architecture of SDN

SDN is organized into three distinct layers, each connected by standard APIs.

+-------------------------------+
|       Application Layer       |   ← Network apps, business policies
+-------------------------------+
               |
         Northbound API
               |
+-------------------------------+
|        Control Layer          |   ← SDN Controller (decision-maker)
+-------------------------------+
               |
         Southbound API
               |
+-------------------------------+
|     Infrastructure Layer      |   ← Physical/virtual switches & routers
+-------------------------------+

Layer Descriptions

LayerComponentsRole
Application LayerRouting apps, firewalls, load balancers, monitoringDefine network policies and intent
Control LayerSDN Controller (e.g., OpenDaylight, ONOS)Translate policies into forwarding rules
Infrastructure LayerOpenFlow switches, routers, OVSExecute rules and forward traffic

APIs

  • Northbound API — connects the controller to applications. Exposes the network as a programmable resource (usually REST-based).
  • Southbound API — connects the controller to network devices. Most common protocol: OpenFlow.
  • East-West API — used when multiple controllers communicate with each other (important for clustering/distributed SDN).
Topic 03 · Foundations

Scalability

Scalability means the ability to handle more devices, more traffic, and larger networks without degrading performance.

⚠️
Key Challenge

A single SDN controller has limited processing capacity. As the network grows, it can become a bottleneck — too many devices sending requests, too many flow rules to install.

Scalability in Data Centers

Data centers host thousands of VMs and containers that constantly move and change. SDN must scale to handle:

  • Large numbers of hosts and flows — millions of flow entries across hundreds of switches
  • VM live migration — when a VM moves to a different server, the network must update instantly
  • Multi-tenancy — many organizations share the same physical data center, each needing isolated virtual networks
  • East-west traffic — most data center traffic flows between servers internally, not just in/out
✅
Solution

Use multiple controllers in a cluster, partition the network into domains, and use distributed data stores to share network state efficiently.

Scalability in Service Provider Networks

  • Hierarchical control — split large networks into domains, each with a local controller; a higher-level controller coordinates across domains
  • Handling millions of flows — provider networks carry massively differentiated traffic
  • Dynamic bandwidth allocation — traffic patterns change constantly; controller must adapt quickly
  • Legacy integration — SDN must coexist with traditional routers and MPLS networks

ISP Automation

ISPs use SDN to automate repetitive network management tasks:

  • Traffic engineering — automatically reroute traffic when links are congested
  • Automated provisioning — bring up new customer connections without manual CLI configuration
  • Policy enforcement — apply bandwidth limits, QoS policies, and routing rules automatically
  • Fast fault recovery — controller calculates and pushes new routes to all affected switches in milliseconds
💡
Key Benefit

Reduces operational cost (OpEx) by replacing time-consuming manual work with software-driven automation.

Topic 04 · Foundations

Reliability

Reliability means the network stays available and functions correctly even when components fail.

⚠️
Single Point of Failure Risk

If the controller crashes, switches may still forward existing traffic using cached rules — but no new rules can be installed and no topology changes handled.

QoS and Service Availability

Quality of Service (QoS) ensures different traffic types get appropriate treatment — video calls need low latency; file transfers can tolerate delay.

SDN improves QoS management through:

  • Centralized traffic monitoring — global view of link utilization; detect congestion before it impacts users
  • Dynamic traffic prioritization — flow rules mark and prioritize traffic; controller updates priorities in real time
  • Traffic engineering — redirect high-priority flows away from congested links automatically
  • SLA enforcement — Service Level Agreements enforced automatically through controller-driven policies

Service Availability Mechanisms

  • Controller redundancy — primary + standby controllers; standby takes over if primary fails
  • Controller clustering — multiple active controllers share load; each switch connects to multiple controllers
  • In-switch fallback rules — pre-installed default rules ensure basic connectivity even if controller is offline
  • Fast failover groups (OpenFlow) — switch automatically switches to backup port without waiting for controller
  Primary Controller ──── Switch ──── Backup Controller
         |                                    |
    (active rules)                   (hot standby, synced)
Topic 05 · Foundations

Consistency

Consistency means all controllers and network devices agree on the same view of the network state at any given time.

Configuration Management

Ensures network-wide policies are applied correctly and uniformly across all devices.

Problems without consistency

  • A new policy via one controller may not reflect in another controller immediately
  • Switches connected to different controllers may apply conflicting rules

Solutions

  • Distributed data stores — replicate configuration across all controllers in real time
  • Two-phase commit — all controllers must acknowledge a change before it takes effect
  • Version control for configs — track every change with timestamps and rollback capability
ModelBehaviorTrade-off
Strong consistencyAll controllers see same state before any change takes effectSafer, but slower
Eventual consistencyChanges propagate over time; temporarily may disagreeFaster, but riskier for critical ops

Access Control Violations

Occur when policies are inconsistently enforced — a device is blocked by one switch but allowed through another due to a stale or missing rule.

Causes

  • Rule update delays between controller and switch
  • Partial failure during policy deployment (some switches updated, others not)
  • Conflicting rules installed by different applications sharing the same controller

Mitigations

  • Atomic rule updates — pre-install new rules before removing old ones
  • Rule conflict detection — controller checks for conflicts before installing rules
  • Consistent updates protocol — network transitions cleanly without violating policy
  • AAA integration — only authorized users/apps can modify network policies
Topic 06 · Foundations

Opportunities & Challenges

✅ Opportunities (Advantages)

  • Easy automation — configure once, apply everywhere automatically
  • Faster service deployment — new services in minutes, not weeks
  • Better traffic management — optimize paths in real time
  • Cost reduction — replace expensive proprietary hardware with commodity switches
  • Cloud-friendly — ideal for dynamic environments
  • Multi-tenancy support — run many isolated virtual networks on shared infrastructure
  • Innovation-friendly — test new protocols without replacing hardware

⚠️ Challenges

  • Controller bottleneck — single controller can get overloaded
  • Single point of failure — controller crash can disrupt the entire network
  • Security risk — controller is a high-value attack target
  • Consistency problem — multiple controllers must stay synchronized
  • Scalability limits — per-flow rules don't scale to millions of flows
  • Migration difficulty — integrating SDN with legacy networks is complex
  • Vendor gaps — not all hardware vendors fully support SDN standards

Use Cases

8.1 Network Access Control (NAC)

NAC controls who can connect to the network and what they are allowed to access after connecting.

  • Identifies devices and users trying to connect
  • Checks compliance (device patched? antivirus up to date?)
  • Grants full access, limited access, or blocks entirely
  • Places suspicious or non-compliant devices in quarantine
  Device requests network access
              |
      NAC checks identity & compliance
              |
     ┌────────────────────┐
     ↓                    ↓
  Compliant           Non-Compliant
     ↓                    ↓
 Full Access          Quarantine / Block
💡
Analogy

NAC is a security guard who checks your ID and health certificate before letting you into a building.

ℹ️
SDN + NAC

The SDN controller enforces NAC decisions dynamically by pushing access-control flow rules to switches in real time — no manual per-port VLAN configuration needed.

8.2 Virtual Customer Edge (vCE)

vCE replaces a physical customer-edge router at a branch site with a software-based virtual router running as a VM, container, or virtual appliance.

Traditional:
  Branch Site → Physical CE Router → Provider Network

vCE:
  Branch Site → Virtual CE (VM/Container) → Provider Network

What vCE Handles

Routing (BGP, OSPF), NAT, VPN tunnels, Firewall and access control

Benefits

No physical hardware shipping. Remote upgrades via software. Faster deployment. Lower cost on standard x86 servers.

8.3 Data Center Optimization

  • Multiple virtual networks on shared hardware — each tenant gets an isolated virtual network
  • Automated provisioning — spin up a new virtual network in seconds
  • Micro-segmentation — each workload isolated, reducing breach blast radius
  • Dynamic load balancing — traffic redistributed automatically when servers overload
  • Reduced hardware costs — virtual switches handle inter-VM traffic on the same host
  Many VMs / Containers
         |
  Virtual Network Layer (OVS + VXLAN)
         |
  Shared Physical Data Center Fabric
         |
  Servers / Storage / Internet
Topic 09 · OpenFlow

Introduction to OpenFlow

OpenFlow is the most widely used southbound protocol in SDN. It defines the communication standard between the SDN controller and network switches.

  Controller  ←──── OpenFlow ────→  Switch
       |                                |
  Makes decisions               Forwards packets

OpenFlow Message Types

MessageDirectionPurpose
Packet-InSwitch → ControllerSwitch sends an unknown packet to the controller
Flow-ModController → SwitchController installs, modifies, or deletes a flow rule
Packet-OutController → SwitchController tells switch to send a specific packet
Flow-StatsBothRequest/response for flow statistics
Port-StatusSwitch → ControllerNotifies controller of port state changes
HelloBothHandshake to establish connection

Flow Table Entry Structure

PartDescription
Match FieldsCriteria to match — IP address, MAC, port number, protocol
PriorityWhich rule takes precedence when multiple rules match
Instructions / ActionsWhat to do — forward to port, drop, send to controller

Packet Processing Flow

  Host sends packet
        ↓
  Switch checks flow table
        ↓
  Match found?
    YES → Execute action (forward / drop)
    NO  → Send Packet-In to controller
        ↓
  Controller decides and sends Flow-Mod
        ↓
  Switch stores new rule and forwards packet

History & Evolution of SDN

SDN emerged from academic research as a response to the limitations of traditional network management at scale.

Timeline

Early 2000s
Research BeginsSeparation of control and data planes researched at universities (RCP, 4D project at CMU/Princeton)
2004
Clean-Slate Design"Clean-slate" network design concept gains momentum; researchers argue for control/forwarding separation
2005–2007
GENI & EthaneGENI project funds early SDN research; Ethane project at Stanford separates flow control from switches
2008
OpenFlow v1.0OpenFlow paper published by McKeown et al. at Stanford — the first formal SDN southbound protocol
2011
ONF FoundedOpen Networking Foundation founded by Google, Facebook, Microsoft and others to promote SDN standards
2012
Google B4Google deploys SDN on its internal B4 backbone between data centers — landmark real-world deployment; OpenFlow 1.3 released
2013
OpenDaylight LaunchedOpenDaylight project launched under the Linux Foundation as the first major open-source SDN controller
2014
ONOSOpen Network Operating System launched targeting carrier-grade SDN deployments
2015–2017
SDN Goes MainstreamSDN adoption grows in data centers (NSX, ACI); NFV and SDN begin to converge
2018–Now
Cloud-Native EraSDN embedded in Kubernetes CNI, intent-based networking (IBN), and 5G network slicing

Why SDN Was Needed

  • Scale problem — thousands of devices needed the same config change manually
  • Vendor lock-in — operators couldn't mix equipment from different vendors
  • Slow innovation — adding a new routing protocol required firmware updates on all hardware
  • Impractical research — testing new ideas required expensive physical labs
Topic 11 · OpenFlow

Control & Data Plane Separation

This is the foundational concept of SDN. Every traditional network device combines two functions — SDN splits them apart.

PlaneRoleWhere it runs
Control PlaneMakes decisions: routing, policy, topology discoverySDN Controller (software)
Data PlaneExecutes decisions: forwards, drops, or modifies packetsSwitches / Routers (hardware)
💡
Simple Analogy

The control plane is the GPS (decides the route); the data plane is the car (drives the route).

Traditional Network

  ┌─────────────────────────────┐
  │    Traditional Switch       │
  │  ┌──────────┐ ┌──────────┐ │
  │  │  Control │ │   Data   │ │
  │  │  Plane   │ │  Plane   │ │
  │  └──────────┘ └──────────┘ │
  └─────────────────────────────┘
 Each device decides independently

SDN

  ┌──────────────────────┐
  │    SDN Controller    │
  │   (Control Plane)    │
  └──────────┬───────────┘
             │ OpenFlow
             ↓
  ┌──────────────────────┐
  │   Switch / Router    │
  │    (Data Plane)      │
  └──────────────────────┘

Benefits of Separation

  • Global visibility — controller sees the entire network, enabling better routing
  • Simplified hardware — switches only match and forward; no complex routing software
  • Faster innovation — new routing algorithms deployed by updating controller software, not switch firmware
  • Consistent policy — one controller enforces the same policy across all devices simultaneously

Topic 14 · OpenDaylight

OpenDaylight Clustering

Clustering means running multiple ODL controller instances together as a single logical controller.

ProblemClustering Solution
Single controller bottleneckDistribute load across multiple instances
Single point of failureIf one node fails, others continue
Limited scalabilityAdd more controller nodes as network grows
Data loss on crashState is replicated across all nodes

How ODL Clustering Works

ODL uses the Akka framework and the Raft consensus algorithm to keep all nodes synchronized.

  • One node is elected as leader for each shard of data
  • All write operations go through the leader
  • Leader replicates changes to follower nodes
  • If leader fails, followers elect a new leader automatically
  ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
  │ Controller 1│    │ Controller 2│    │ Controller 3│
  │  (Leader)   │◄──►│  (Follower) │◄──►│  (Follower) │
  └──────┬──────┘    └──────┬──────┘    └──────┬──────┘
         │                  │                  │
         └──────────────────┴──────────────────┘
                    Shared Network State
                   (Raft-replicated shards)

Shard-Based Data Partitioning

ODL splits its datastore into shards. Different shards can have different leaders, distributing write load. Common shards:

  • default — general topology data
  • inventory — device/node information
  • topology — link-state information

Model-Driven Service Abstraction Layer (MD-SAL)

MD-SAL is the core service bus and data management layer inside OpenDaylight. It connects all internal components and applications through a common, model-driven framework.

  Applications / Plugins
          ↓
       MD-SAL
    ┌────────────────────────────┐
    │  Data Store  │  RPC Bus   │
    │  Notification│  Service   │
    └────────────────────────────┘
          ↓

Key Functions

Data Store ManagementStores and retrieves all network state (config and operational)
RPC (Remote Procedure Call)Components call services provided by other components
NotificationsPublish-subscribe system for internal events (e.g., "new node connected")

MD-SAL uses YANG (Yet Another Next Generation) — a data modeling language — to define the structure of configuration/state data, RPC inputs/outputs, and notification formats. This makes ODL self-documenting and interoperable.

Topic 16 · OpenDaylight

Internal Datastore

The Internal Datastore is the database inside OpenDaylight that stores all network state information. It is built on top of MD-SAL and uses YANG-modeled data trees.

Two Types of Data Trees

TreeContainsManaged By
Config DatastoreIntended/desired state — what you want the network to look likeOperator or application writes
Operational DatastoreActual/current state — what the network looks like right nowController and devices write
ℹ️
Example

You configure a flow rule → it enters the config datastore. Once the rule is confirmed installed on the switch, it appears in the operational datastore.

Key Properties

  • In-memory storage — fast reads and writes for real-time network control
  • Persistent backup — state can be persisted to disk and restored on restart
  • Transactional — changes applied atomically; partial failures are rolled back
  • Replicated — in a clustered setup, replicated across all controller nodes using Raft

Accessing via RESTCONF

# Read config datastore
GET http://localhost:8181/restconf/config/

# Read operational datastore
GET http://localhost:8181/restconf/operational/

# Get all network nodes
GET http://localhost:8181/restconf/operational/opendaylight-inventory:nodes
Topic 17 · OpenDaylight

OpenFlow Plugin

The OpenFlow Plugin is the southbound component in OpenDaylight that enables communication with OpenFlow-capable switches. Without it, ODL cannot talk to OpenFlow switches.

  OpenDaylight Controller
          ↓
  OpenFlow Plugin
   - translates MD-SAL data to OpenFlow wire format
   - manages OpenFlow connections (TCP port 6633 / 6653)
          ↓
  OpenFlow Switch (OVS / hardware switch)

What the Plugin Does

  • Establishes and maintains OpenFlow connections with switches
  • Translates flow rule objects (from MD-SAL) into OpenFlow binary messages
  • Receives Packet-In events from switches and publishes them to MD-SAL
  • Installs Flow-Mod messages onto switches when rules are added/changed
  • Collects switch statistics and updates the operational datastore

Supported OpenFlow Versions

VersionKey Features
OpenFlow 1.0Single flow table, basic match fields
OpenFlow 1.3Multiple flow tables, group tables, meters (for QoS)

ODL's OpenFlow plugin supports both versions and auto-negotiates with connected switches.

Flow Pipeline (OpenFlow 1.3)

  Packet arrives at switch
        ↓
  Table 0 (first table)
        ↓ (match / miss)
  Table 1 → Table 2 → ... → Table N
        ↓
  Final action: output to port / drop / send to controller
Topic 18 · Lab Tools

Open vSwitch (OVS) Concepts

Open vSwitch (OVS) is a production-quality, open-source virtual switch designed for virtualized server environments. It is the most widely used virtual switch in SDN labs and cloud platforms (OpenStack, Kubernetes).

Key Features

  • Supports OpenFlow — can be controlled by any SDN controller
  • Supports OVSDB — configuration (bridges, ports, tunnels) can be managed remotely
  • Supports VXLAN, GRE, STT — creates overlay tunnels between hosts
  • 802.1Q VLAN tagging and trunking
  • Bonding — link aggregation for redundancy
  • Works with the Linux kernel for high-performance packet forwarding
  VM1    VM2    VM3
   |      |      |
  ┌────────────────────┐
  │    OVS Bridge      │  ← virtual switch (flow table)
  └────────┬───────────┘
           │
  Physical NIC → Physical Network → Other Hosts

Key OVS Components

ComponentRole
ovs-vswitchdMain daemon that manages the virtual switch
ovsdb-serverDatabase server storing OVS configuration
ovs-vsctlCLI tool to configure OVS (add bridges, ports)
ovs-ofctlCLI tool to manage OpenFlow flows on OVS
ovs-dpctlCLI tool to manage the kernel datapath

Common OVS Commands

# Create a new bridge (virtual switch)
ovs-vsctl add-br br0

# Add a physical port to the bridge
ovs-vsctl add-port br0 eth0

# Set controller for the bridge
ovs-vsctl set-controller br0 tcp:<controller_ip>:6633

# Create a VXLAN tunnel
ovs-vsctl add-port br0 vxlan0 -- \
  set interface vxlan0 type=vxlan options:remote_ip=<remote_host_ip>

# Show all flows on a bridge
ovs-ofctl dump-flows br0

Mininet Overview

Mininet is a network emulator that creates a complete virtual network — hosts, switches, links, and a controller — on a single Linux machine. It is the standard tool for SDN research and learning.

Hosts

Lightweight Linux processes with their own network namespace

Switches

OVS instances that support OpenFlow rules

Links

Virtual Ethernet pairs with configurable bandwidth and delay

Controller

Local or remote (e.g., OpenDaylight) over IP

Starting Mininet

# Basic: 2 hosts + 1 switch + default controller
sudo mn

# Tree topology: depth 2, fanout 2
sudo mn --topo=tree,2,2

# Connect to a remote controller (e.g., OpenDaylight)
sudo mn --controller=remote,ip=127.0.0.1,port=6633 --topo=linear,3

# Single switch with 4 hosts
sudo mn --topo=single,4

Common CLI Commands

nodes            # List all nodes
links            # Show all links
pingall          # Ping between all hosts
iperf h1 h2      # Run iperf test between hosts
xterm h1         # Open terminal for host h1
h1 ifconfig      # Show interfaces of h1
sh ovs-ofctl dump-flows s1   # Show OVS flows

Topic 20 · Lab Tools

L2 Switch Application

L2Switch is a built-in application in OpenDaylight that makes ODL behave like a Layer 2 learning switch — learning MAC addresses and forwarding frames intelligently.

How a Learning Switch Works

  Host sends frame
        ↓
  Switch: "I don't know this MAC" → Flood to all ports
        ↓
  Destination replies → Switch learns its MAC + port
        ↓
  Flow rule installed → Future frames go directly

What L2Switch Does in ODL

  1. Receives Packet-In — when a switch sends an unknown packet to ODL
  2. Learns MAC-to-port mapping — stores which host is on which switch port
  3. Installs flow rules — pushes Flow-Mod back to switch for direct forwarding
  4. Handles topology — uses LLDP to discover the network topology and avoid loops
  ODL + L2Switch
        |
  Packet-In (unknown destination)
        |
  L2Switch learns MAC → installs Flow-Mod
        |
  Future packets forwarded directly (no controller involvement)
ℹ️
Loop Prevention

L2Switch uses Spanning Tree Protocol (STP) or topology-aware path selection to prevent forwarding loops in networks with redundant links.

Installing L2Switch in ODL

feature:install odl-l2switch-switch
feature:install odl-l2switch-switch-ui  # includes topology UI

OpenDaylight & AAA

AAA stands for Authentication, Authorization, and Accounting — the security framework that protects access to the SDN controller.

TermMeaningQuestion it Answers
AuthenticationVerify identity"Who are you?"
AuthorizationCheck permissions"What are you allowed to do?"
AccountingLog activity"What did you do, and when?"
⚠️
Why AAA is Critical

The SDN controller has complete network control. An unauthorized user with API access could install malicious flow rules, block legitimate traffic, or expose private topology data.

              ↓

OVSDB Virtualization

OVSDB (Open vSwitch Database Management Protocol) is a protocol used to configure and manage Open vSwitch — specifically to create and modify its database of bridges, ports, interfaces, and tunnels.

💡
OpenFlow vs. OVSDB

OpenFlow tells the switch how to route traffic. OVSDB tells the switch how to be built — creating bridges, ports, and tunnels.

ProtocolControlsUsed For
OpenFlowTraffic forwarding rules (flow table)Deciding where packets go
OVSDBSwitch structure and configurationCreating bridges, ports, tunnels

What OVSDB Can Do

  • Create and delete bridges (virtual switches)
  • Add and configure ports and interfaces
  • Create VXLAN, GRE, or STT tunnels between hosts
  • Configure VLANs on ports
  • Set QoS policies on interfaces

OVSDB Virtualization Use Case

  ODL Controller
      ↓ OVSDB (TCP port 6640)
  OVS on Host A ──── VXLAN Tunnel ──── OVS on Host B
      |                                      |
   Tenant A VM                          Tenant A VM
  1. Overlay Network Creation — OVSDB creates VXLAN tunnels between all hypervisors
  2. Dynamic Provisioning — when a new VM is created, controller configures local OVS via OVSDB
  3. Isolation — each tenant's traffic encapsulated in different VXLAN VNIs (virtual network identifiers)

Application Intents & Group-Based Policy (GBP)

GBP allows network policies to be defined using high-level intent rather than low-level IP addresses and port numbers. The controller automatically translates intent into flow rules.

❌ Traditional ACL (Low-level)

"Allow TCP port 443 from 10.0.0.5 to 10.0.1.3, deny all else"

✅ GBP (High-level Intent)

"Web servers can communicate with DB servers over HTTPS"

Key Concepts

TermMeaning
EndpointAn individual device, VM, or container
Endpoint Group (EPG)A logical group with the same role (e.g., "Web Servers")
ContractPolicy defining what communication is allowed between two EPGs
SubjectA grouping of rules inside a contract
ClauseA condition that determines when a subject applies
 
  ┌────────────────┐   Contract: HTTP allowed   ┌────────────────┐
  │  EPG: Web      │ ──────────────────────────► │  EPG: Database │
  │  (Web Servers) │                             │  (DB Servers)  │
  └────────────────┘                             └────────────────┘

  ┌────────────────┐                             ┌────────────────┐
  │  EPG: Dev PCs  │ ──── No Contract ──────────► │  EPG: Database │
  │                │   (blocked by default)       │                │
  └────────────────┘                             └────────────────┘

GBP vs Traditional ACLs

Traditional ACLGBP
Based on IPs and portsBased on roles and groups
Must be rewritten when IPs changePolicy stays when VMs move
Hard to understand and auditHuman-readable intent
Applied per deviceApplied network-wide automatically
Topic 24 · Advanced Features

Service Function Chaining (SFC)

SFC is an SDN/NFV technique that routes network traffic through a predefined, ordered sequence of network service functions before reaching its destination.

Problem SFC Solves

Without SFC, traffic goes directly via shortest path. Enterprises need traffic to pass through security and optimization services first. Traditionally, this required manually inserting physical appliances. SFC allows services to be applied dynamically using virtual network functions (VNFs).

  Client Traffic
        ↓
  ┌─────────────────────────────────────┐
  │          Service Function Chain     │
  │   Firewall → Load Balancer → IDS   │
  └─────────────────────────────────────┘
        ↓
  Destination Server

Key Components

ComponentRole
Service Function (SF)A network function that processes traffic (e.g., firewall)
Service Function Forwarder (SFF)A switch that steers traffic to the right SF
Service Function Path (SFP)The defined order of SFs that traffic must traverse
Network Service Header (NSH)Metadata attached to packets to identify which chain they belong to
ClassifierIdentifies which traffic should enter which chain
ℹ️
SFC in OpenDaylight

ODL supports SFC through the odl-sfc feature set. The controller configures SFFs (usually OVS instances) to steer traffic, and uses NSH headers to track which chain a packet belongs to.

Topic 25 · Advanced Features

LISP Flow Mapping

LISP (Locator/ID Separation Protocol) separates a device's identity (what it is) from its location (where it is) in the network.

In traditional IP networking, an IP address serves both purposes. When a device moves, its IP changes, breaking connections. LISP solves this with two separate namespaces:

NamespaceTermMeaning
IdentityEID (Endpoint Identifier)Stable address that stays with the device even when it moves
LocationRLOC (Routing Locator)Address of the router/tunnel endpoint currently serving the device
 
  Device (EID: 10.0.0.1)
        ↓
  Ingress Tunnel Router (ITR)
        ↓  asks: "Where is EID 10.0.0.1?"
  LISP Map Server / Map Resolver
        ↓  replies: "RLOC is 192.168.1.5"
  Egress Tunnel Router (ETR) at 192.168.1.5
        ↓
  Destination device

LISP in OpenDaylight

ODL includes a LISP Flow Mapping service acting as a LISP Map Server and Map Resolver. ODL stores EID-to-RLOC mappings and responds to mapping queries from network nodes.

Use Cases for LISP

Use CaseHow LISP Helps
VM mobilityVM keeps its EID (IP) when moved between data centers
Multi-homingOne EID maps to multiple RLOCs for redundancy
Traffic engineeringController changes RLOC mapping to redirect traffic
Large-scale routingReduces routing table size using compact RLOC space
IoT / mobile networksDevices roam without IP address changes
Topic 26 · Advanced Features

Virtual Tenant Networks (VTN)

VTN is an OpenDaylight application that allows multiple users (tenants) to have their own isolated virtual networks running on top of a shared physical network infrastructure.

  Shared Physical Network
          ↓
  ┌────────────────────────────────┐
  │  Virtual Network: Tenant A    │  ← Isolated
  │  Virtual Network: Tenant B    │  ← Isolated
  │  Virtual Network: Tenant C    │  ← Isolated
  └────────────────────────────────┘

VTN Components

ComponentDescription
VTNTop-level virtual network for one tenant
vBridgeA virtual Layer 2 network (like a virtual LAN) inside a VTN
vRouterA virtual Layer 3 router that connects vBridges within a VTN
vInterfaceA virtual port that connects a host/VM to a vBridge
Flow FilterApplies traffic policies (allow, deny, redirect) within a VTN
Flow ConditionMatch criteria used by flow filters

VTN Architecture

  Tenant A VTN
    ├── vBridge A1 (192.168.1.0/24)
    │     ├── vInterface (Host 1)
    │     └── vInterface (Host 2)
    └── vBridge A2 (192.168.2.0/24)
          └── vInterface (Host 3)

  Tenant B VTN
    └── vBridge B1 (10.0.0.0/24)
          ├── vInterface (Host 4)
          └── vInterface (Host 5)

VTN Flow Filters

  • Pass — allow traffic matching the condition
  • Drop — silently discard traffic
  • Redirect — send traffic through a specific service (e.g., SFC integration)

Benefits of VTN

  • Strong isolation — tenants cannot see or interfere with each other
  • Flexible topology — each tenant defines their own network topology independently
  • Centralized management — all VTNs managed from the single ODL controller
  • Cloud-ready — integrates naturally with OpenStack and similar platforms
  • Scalable — many tenants coexist without separate physical infrastructure
