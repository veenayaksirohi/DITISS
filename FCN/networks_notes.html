Part 1

Switching Types

1.1 Circuit Switching

A dedicated physical path is established end-to-end before data transfer starts. The entire communication uses the same path, like a traditional telephone call.

Phases

  1. Setup — Call request and connection setup.
  2. Data Transfer — Data flows continuously over the fixed path.
  3. Teardown — Connection is released after transfer.
  ┌────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌─────────────┐
  │ Source │════│ Switch-A │════│ Switch-B │════│ Switch-C │════│ Destination │
  └────────┘    └──────────┘    └──────────┘    └──────────┘    └─────────────┘
                ══════════════════════════════════════════════════
                     Dedicated path reserved for entire call
                     No other traffic can use this path
                     Path is IDLE if no data is being sent → waste

✅ Pros

Low delay during transfer — path is always ready.

❌ Cons

Wastes bandwidth when path is idle.

1.2 Message Switching

The entire message is treated as a single unit. Each intermediate node stores the whole message, then forwards it (store-and-forward).

  ┌────────┐     ┌────────┐     ┌────────┐     ┌─────────────┐
  │ Source │─MSG→│ Node-1 │─MSG→│ Node-2 │─MSG→│ Destination │
  └────────┘     │ STORE  │     │ STORE  │     └─────────────┘
                 │   ↓    │     │   ↓    │
                 │FORWARD │     │FORWARD │
                 └────────┘     └────────┘
         Entire message must be stored at each node before forwarding
         High delay — especially for large messages

✅ Pros

Efficient for bursty traffic.

❌ Cons

High delay due to full-message storage; rarely used today.

1.3 Packet Switching

Breaks the message into smaller packets. Two sub-types:

a) Datagram Switching (Connectionless)

Each packet is routed independently — no fixed path. Different packets may take different routes; reassembly happens at the receiver. Every packet carries full source & destination addresses.

                              ┌──────┐
                   ┌──P1────→ │ SW-A │──P1──────────────────────────→ ┐
                   │          └──────┘                                 │
  ┌────────┐       │          ┌──────┐                       ┌─────────────┐
  │ Source │───────┤──P2────→ │ SW-B │──P2─────────────────→│ Destination │
  └────────┘       │          └──────┘                       └─────────────┘
                   │          ┌──────┐  ┌──────┐                      ↑
                   └──P3────→ │ SW-A │─→│ SW-B │──P3─────────────────┘
                              └──────┘  └──────┘
  ● Each packet carries full source & destination address
  ● Packets may arrive OUT OF ORDER (P3 may arrive before P1)
  ● Reassembly happens at Destination only

✅ Pros

High efficiency; resilient to link failures.

❌ Cons

Variable delay; out-of-order arrival possible.

b) Virtual Circuit Switching (Connection-Oriented)

A logical path (virtual circuit) is set up before data transfer. All packets follow the same pre-decided route using a Virtual Circuit Identifier (VCI) instead of full addresses.

Phases

  1. VC Establishment — Setup packet reserves the path.
  2. Data Transfer — All packets follow the established VC.
  3. VC Teardown — Logical connection is released.
  Phase 1 – VC Establishment (logical path reserved):
  ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐   ┌─────────────┐
  │ Source │═══│ Node-1 │═══│ Node-2 │═══│ Node-3 │═══│ Destination │
  └────────┘   └────────┘   └────────┘   └────────┘   └─────────────┘
               ══════════════════════════════════════════════
                     Virtual Circuit VC1 (pre-established)
                     ● Only VCI label in each packet header
                     ● No per-packet routing decision

  Phase 2 – Data Transfer (all packets follow VC1, arrive in order):
  [VC1,P1] ──→ ──→ ──→ ──→ ──→  In-order delivery ✅
  [VC1,P2] ──→ ──→ ──→ ──→ ──→
  [VC1,P3] ──→ ──→ ──→ ──→ ──→

  Phase 3 – VC Teardown: connection released, resources freed

✅ Pros

Low per-packet delay; ordered delivery guaranteed.

❌ Cons

Less robust to link failure; setup overhead.

Part 2

Ethernet Forwarding Methods

2.1 Store-and-Forward Switching

The switch receives the entire frame into its buffer before making a forwarding decision. It checks the FCS (CRC) for integrity and drops invalid frames.

  ┌──────┐  Full Frame  ┌────────────────────────────────────────┐  Frame  ┌──────┐
  │ Host │─────────────→│           Switch Buffer                │────────→│ Host │
  │  A   │              │  [1] Receive entire frame into buffer  │         │  B   │
  └──────┘              │  [2] Recalculate FCS / CRC             │         └──────┘
                        │  [3] CRC OK?   → Forward  ✅           │
                        │      CRC Fail? → DROP     ❌           │
                        └────────────────────────────────────────┘

✅ Pros

Most reliable — no error propagation.

❌ Cons

Highest latency of all methods.

2.2 Cut-Through Switching

Forwarding begins before the whole frame arrives. Two variants:

a) Fast-Forward Switching

Begins forwarding as soon as the destination MAC address is read (first 6 bytes only). Does NOT check FCS.

  ┌──────┐  Bytes 1–6 (Dst MAC)  ┌───────────────────────────────────┐  Forwarding!  ┌──────┐
  │ Host │──────────────────────→│ Switch reads Dst MAC (6 bytes)    │──────────────→│ Host │
  │  A   │                       │ Immediately starts forwarding     │               │  B   │
  └──────┘  Bytes 7–n ──────────→│ (rest of frame still arriving)   │               └──────┘
            still arriving...    │ ❌ No FCS check — errors propagate│
                                 └───────────────────────────────────┘

✅ Pros

Lowest latency of all switching methods.

❌ Cons

Can forward corrupted frames.

b) Fragment-Free Switching

Improved cut-through — buffers the first 64 bytes before forwarding. Collisions produce fragments shorter than 64 bytes (runts), so this filters them. Still does NOT check full FCS.

  ┌──────┐  Frame  ┌────────────────────────────────────────────┐  Frame  ┌──────┐
  │ Host │────────→│  Switch buffers first 64 bytes             │────────→│ Host │
  │  A   │         │  Is it a runt? (< 64 bytes?) → DROP ❌     │         │  B   │
  └──────┘         │  Not a runt?                 → Forward ✅   │         └──────┘
                   │  (No full FCS check beyond byte 64)        │
                   └────────────────────────────────────────────┘

✅ Pros

Filters collision fragments (runts).

❌ Cons

Does not catch bit errors beyond byte 64.

2.3 Quick Comparison

MethodBuffer AmountError CheckLatencyBest For
Store-and-ForwardEntire frameFull FCS/CRCHighestReliability
Fast-ForwardFirst 6 bytes (MAC DA)NoneLowestSpeed
Fragment-FreeFirst 64 bytesRunt/collision onlyMedium–LowBalance
Part 3

Port Security

Port security limits which MAC addresses can send traffic through a switch access port, preventing unauthorized devices (rogue laptops, switches) from connecting.

3.1 Violation Modes

ModeActionLogs?Port Stays Up?
ProtectDrops violating frames silently❌ No✅ Yes
RestrictDrops frames + logs + increments counter✅ Yes✅ Yes
ShutdownErr-disables the port; stops all traffic✅ Yes❌ No
⚠️
Default on Cisco IOS = Shutdown

If you don't specify a violation mode, the port will be err-disabled on the first violation.

3.2 Sticky MAC Addresses

Static MACs

Manually configured; survive reloads automatically.

Dynamic MACs

Learned automatically but lost on reload.

Sticky MACs

Dynamically learned but saved to running-config. Survive reboot only if you run write memory.

  ┌─────────────────────┐   Frame (src: aabb.cc00.0100)   ┌───────────────────────────────┐
  │  PC (aabb.cc00.0100)│ ──────────────────────────────→ │      Switch Port Fa0/1        │
  └─────────────────────┘                                  │                               │
                                                           │  ① Receives first frame       │
                                                           │  ② Learns MAC dynamically     │
                                                           │  ③ Sticky: saves to config ──→│
                                                           │     switchport port-security  │
                                                           │      mac-address sticky       │
                                                           │      aabb.cc00.0100           │
                                                           │  ④ write memory → survives ✅ │
                                                           │  ④ no write → lost on reload ❌│
                                                           └───────────────────────────────┘

3.3 Aging Timers

Controls how long a dynamically learned secure MAC stays bound to a port. By default, secure MACs never age out.

TypeBehaviour
AbsoluteTimer starts at learn time; MAC removed when timer expires, even if device is active.
InactivityTimer resets on every frame; MAC removed only after no traffic for the set time.
ℹ️
Static MACs never age out.

Only dynamic and sticky MACs are subject to aging timers.

            |  Switch Access Port Fa0/1   |
            |  max: 2 | sticky | aging: 10 min inactivity |
            +-----------------------------+
                     |
  +------------------+    ✅ MAC-A → Allowed (sticky learned)
  |  PC (MAC-A)      |──→ ✅ MAC-B → Allowed (sticky learned)
  +------------------+
  +------------------+    ❌ MAC-C → VIOLATION
  |  PC (MAC-C)      |──→    Restrict: drop + log
  +------------------+       Shutdown: port err-disabled
Part 4

Spanning Tree Protocol (STP)

Why STP is Needed – Layer 2 Loops

Real networks use redundant links between switches for fault tolerance. But Ethernet frames have no TTL — nothing stops a frame from looping forever. Three simultaneous problems occur:

① Broadcast Storm

A single ARP request loops endlessly → 100% CPU on all switches → complete network collapse.

② MAC Flapping

MAC table entries flip-flop continuously → switches cannot forward correctly.

③ Duplicate Frames

Same unicast frame arrives at destination multiple times → TCP connections break.

  WITHOUT STP (Loop Present):
                       PC-A
                        |
                       SW1
                      /    \
                   Link1    Link2
                    /          \
                  SW2 ─────── SW3
                       Link3

  Step 1: PC-A sends broadcast → SW1 floods out Link1 AND Link2.
  Step 2: SW2 via Link1 → floods via Link3; SW3 via Link2 → floods back.
  Step 3: Both switches receive AGAIN → infinite loop.
  ┌──────────────────────────────────────────────────┐
  │  BROADCAST STORM — Network CRASHES               │
  └──────────────────────────────────────────────────┘

  WITH STP (Loop Broken):
                       PC-A
                        |
                      SW1  ← Root Bridge (lowest BID)
                      /    \
                  Link1(DP)  Link2(DP)
                   /               \
                 SW2(RP) ──── SW3(RP)
                         Link3
                  SW2=Designated ✅  SW3=BLOCKED ❌
  ┌──────────────────────────────────────────────────┐
  │  Loop BROKEN — Backup path ready if SW2 fails    │
  └──────────────────────────────────────────────────┘
Problem Without STPSTP Solution
Broadcast storms crash the networkBlocks redundant ports to eliminate loops
MAC table instability / flappingStable topology = stable MAC learning
Duplicate frame deliverySingle forwarding path per segment
No Layer 2 TTLSTP acts as loop-prevention mechanism

4.3 Bridge ID (BID) & Priority

  Classic 802.1D BID:
  ┌──────────────────┬──────────────────────────────┐
  │  Priority (2 B)  │   System ID / MAC addr (6 B)  │
  └──────────────────┴──────────────────────────────┘

  Extended System ID (PVST+/Rapid PVST+):
  Priority field = Bridge Priority + VLAN ID
  Example: 32768 + 10 = 32778

  Root Bridge Election: Lowest BID wins.
  If priority equal → lowest MAC address wins.

VLANs & Inter-VLAN Routing

A VLAN is a logical LAN on a physical switch — it divides one switch into multiple broadcast domains. Devices in the same VLAN communicate directly; different VLANs require Layer 3 routing.

6.1 VTP (VLAN Trunking Protocol)

Cisco-proprietary protocol that synchronizes VLAN information across switches in a VTP domain.

ModeCan Create VLANs?Syncs with Domain?
Server✅ Yes✅ Yes — sends & receives updates
Client❌ No✅ Yes — receives only
Transparent✅ Yes (locally)❌ No — forwards but ignores updates
VersionKey Feature
VTP v1Basic VLAN sync; normal VLANs only (1–1005)
VTP v2Token Ring support; minor improvements
VTP v3Extended VLANs (1006–4094); primary/secondary server roles; better security

6.2 802.1Q Tagging

Standard for VLAN tagging on trunk links. Inserts a 4-byte tag into the Ethernet frame, increasing max frame size from 1518 → 1522 bytes.

Port TypeFrame TypeVLANs Supported
Access PortUntagged (to host)One VLAN only
Trunk PortTagged (between switches/routers)Many VLANs

6.3 Router-on-a-Stick

One physical router interface on a trunk link. Router uses subinterfaces (e.g., G0/0.10, G0/0.20) — one per VLAN.

  PC-A (VLAN 10) ──→ Switch ──[trunk]──→ Router
                                          ├── G0/0.10 (gateway for VLAN 10)
                                          └── G0/0.20 (gateway for VLAN 20)
                                                  ↓
                                          PC-B (VLAN 20)
  ✅ Simple to configure
  ❌ Single physical link = single point of failure

6.4 Layer 3 Switching – SVIs

A Switched Virtual Interface (interface Vlan10) is a logical VLAN interface on a Layer 3 switch with an IP address acting as the default gateway.

  ┌──────────────────────────────────────────────────────┐
  │              Layer 3 Switch                          │
  │                                                      │
  │  interface Vlan10                                    │
  │  ip address 10.0.1.1 255.255.255.0  ◄── VLAN 10 GW │
  │                                                      │
  │  interface Vlan20                                    │
  │  ip address 10.0.2.1 255.255.255.0  ◄── VLAN 20 GW │
  │                                                      │
  │  Routes between VLANs in hardware ✅ (much faster)   │
  └──────────────────────┬───────────────────────────────┘
                         │
         ┌───────────────┴────────────────┐
         │                                │
  ┌──────────────────┐          ┌──────────────────┐
  │  VLAN 10 — PCs   │          │  VLAN 20 — Servers│
  │  10.0.1.0/24     │          │  10.0.2.0/24      │
  └──────────────────┘          └──────────────────┘

Infrastructure Security & ACLs

7.1 AAA Framework

FunctionQuestion AnsweredExamples
Authentication"Who are you?"Username/password, certificates, tokens
Authorization"What can you do?"Exec-privilege level, allowed commands

7.2 RADIUS

Open standard client-server AAA protocol. Transport: UDP | Ports: 1812 (auth), 1813 (accounting). Authentication + Authorization are combined in one exchange.

  ┌──────────────────────┐   Access-Request (UDP 1812)    ┌──────────────────────┐
  │   Network Device     │ ──────────────────────────────→│    RADIUS Server     │
  │  (Switch / Router)   │                                │                      │
  │                      │ ←── Access-Accept / Reject ────│  Auth + Authz        │
  │  User logs in ──────→│    (combined in one exchange)  │  combined in one     │
  │                      │                                │  response            │
  │                      │ ──── Accounting (UDP 1813) ───→│                      │
  └──────────────────────┘                                └──────────────────────┘

7.3 TACACS+

Cisco-enhanced AAA protocol. Transport: TCP | Port: 49. Separates Authentication, Authorization, and Accounting into three independent exchanges. Supports per-command authorization.

  ┌──────────────────────┐  ① Auth Req (TCP 49)   ┌──────────────────────┐
  │   Network Device     │ ──────────────────────→│   TACACS+ Server     │
  │  (Router / Switch)   │ ←── Auth Response ─────│                      │
  │                      │                        │  ① Authentication    │
  │                      │ ──② Authorization ────→│  ② Authorization     │
  │                      │ ←── Authz (per-cmd) ───│  ③ Accounting        │
  │                      │                        │  (all 3 separate)    │
  │                      │ ──③ Accounting ────────→│  Entire pkt encrypted│
  └──────────────────────┘                        └──────────────────────┘

8.4 PPP & MLPPP

PPP (Point-to-Point Protocol) is a Layer 2 protocol for serial WAN links providing: Authentication (PAP/CHAP), encapsulation, error detection.

MLPPP combines multiple physical serial links into one logical PPP bundle, increasing bandwidth and supporting load-sharing.

Root Port Selection Tiebreakers

  1. Lowest Root Path Cost

Alternate vs Backup Port

Alternate Port

Backup path to the Root Bridge via a different path. Instantly transitions to forwarding when Root Port fails — key to RSTP's fast convergence.

Backup Port

Backup to the Designated Port on the same segment on the same switch. Only appears when two ports on the same switch connect to the same segment (usually via a hub).

         SW1 (Root Bridge)
         /              \
       (DP)             (DP)    ← All SW1 ports = Designated Ports
       /                   \
     SW2                   SW3
     (RP)                  (RP) ← Root Ports face toward SW1
       \                   /
        \                 /
      (DP)\─────────────/(AP)  ← SW2 wins DP on this link
                                   SW3 port = Alternate Port (blocking ❌)
Part 10

EtherChannel (LACP & PAgP)

EtherChannel bundles multiple physical links between switches into one logical link. STP sees the bundle as a single interface, so no individual links get blocked. Provides increased bandwidth and redundancy.

  SW1 ══════════════════ SW2
       4 × 1 Gbps links
       = 1 logical 4 Gbps EtherChannel

  "STP sees ONE link — no ports blocked inside the bundle"

Part 11

DHCP Snooping & Dynamic ARP Inspection

11.1 DHCP Snooping

Layer 2 security feature that protects against rogue DHCP servers. Acts as a firewall between DHCP traffic and the real DHCP server.

Port TypeConnected ToDHCP Replies
TrustedLegitimate DHCP server / uplink switch✅ Allowed
UntrustedEnd devices (PCs, printers)❌ DROPPED

Protects against: Rogue DHCP servers (attacker handing out wrong IPs/gateways) and DHCP starvation attacks (flooding DISCOVER messages to exhaust the pool).

  [Legit DHCP Server] ──(Trusted)──→ SW1 ──(Untrusted)──→ PCs
                                       │
                                 (Untrusted)
                                       │
                           [Rogue DHCP Server] ← REPLY DROPPED ❌

11.2 Dynamic ARP Inspection (DAI)

Layer 2 security feature that prevents ARP spoofing / ARP poisoning. Validates ARP packets against the DHCP Snooping Binding Table.

  PC-A (10.0.1.10 / MAC-A) ──── SW1 ──── PC-B (10.0.1.20 / MAC-B)
                                 │
                    [Attacker: "I am 10.0.1.20, my MAC = ATTACK"]
                                 │
                    DAI checks binding table:
                    10.0.1.20 should be MAC-B → MISMATCH → DROP ❌

11.3 DHCP Snooping vs DAI

FeatureDHCP SnoopingDAI

Part 12

IPv6 SLAAC

Stateless Address Autoconfiguration — an IPv6 host configures its own address without a DHCP server. Uses NDP messages (RS/RA) and EUI-64 for the interface ID. Defined in RFC 4862.

Step-by-Step Process

  1. Generate Link-Local Address — prefix fe80::/10 + EUI-64 interface ID from MAC.
  2. DAD on Link-Local — host sends NS for its own address. No reply = unique ✅.
  3. Send Router Solicitation (RS) — to ff02::2: "Is there a router on this link?"
  4. Receive Router Advertisement (RA) — router replies with network prefix, default gateway (its Link-Local), and M/O flags.
  5. Build Global Unicast Address — Prefix from RA + EUI-64 interface ID.
  6. DAD on Global Unicast — confirms it's unique before using it.
  Host                                      Router
   │── Step 1: Generate Link-Local ──────────│
   │   (fe80::... via EUI-64)                │
   │── Step 2: DAD (NS for own addr) ────────│
   │   (No reply = unique ✅)                │
   │── Step 3: RS ────────────────────────── ff02::2
   │                                          │
   │←─ Step 4: RA (prefix, gateway, flags) ──│
   │   prefix: 2001:db8::/64                 │
   │   gateway: fe80::1 | M=0, O=0 → SLAAC  │
   │── Step 5: Build Global Unicast ─────────│
   │   2001:db8::/64                 │
   │── Step 6: DAD on Global addr ───────────│
   │   Host fully configured! ✅              │

RA Flags (M and O)

M FlagO FlagModeMeaning
00Pure SLAACHost self-configures address + uses RA for everything
01SLAAC + Stateless DHCPv6Self-configures address; gets DNS etc. from DHCPv6
1—Stateful DHCPv6Host must get address from DHCPv6 server

EUI-64 Interface ID Generation

  1. Take 48-bit MAC: 1a:2b:3c:4d:5e:6f
  2. Split in half: 1a:2b:3c | 4d:5e:6f
  3. Insert ff:fe in middle: 1a:2b:3c:ff:fe:4d:5e:6f
  4. Flip the 7th bit (Universal/Local bit) of the first byte.
  5. Result = 64-bit Interface ID appended to network prefix.

Part 14

NAT64

NAT64 allows IPv6-only hosts to communicate with IPv4-only servers by translating between IPv6 and IPv4 addresses at the network boundary. Works alongside DNS64.

How NAT64 Works

  1. IPv6 host queries DNS64 for an IPv4-only domain (example.com).
  2. DNS64 finds only an IPv4 A record (93.184.216.34). It synthesizes an AAAA record by embedding the IPv4 address into the NAT64 prefix (64:ff9b::/96):
    Synthesized AAAA: 64:ff9b::5db8:d822
  3. Host sends IPv6 packet to 64:ff9b::5db8:d822.
  4. NAT64 gateway intercepts, extracts IPv4 destination (93.184.216.34), translates IPv6→IPv4, forwards.
  5. IPv4 server replies → gateway translates IPv4→IPv6 → sends back to host.
  IPv6 Host          NAT64 Gateway            IPv4 Server
  (2001:db8::1)      (64:ff9b::/96)         (93.184.216.34)
       │                    │                      │
       │── IPv6 packet ────→│                      │
       │  Dst: 64:ff9b::    │── IPv4 packet ──────→│
       │       5db8:d822    │  Dst: 93.184.216.34  │
       │                    │                      │
       │                    │←─ IPv4 reply ─────── │
       │←─ IPv6 reply ──────│                      │
       │  Src: 64:ff9b::    │                      │
       │       5db8:d822    │                      │

High-Level Data Link Control — a Layer 2 protocol for serial point-to-point WAN links. Bit-oriented, data transmitted as a continuous bit stream. Bit Stuffing

Problem: Flag byte = 01111110 (six consecutive 1s). If data also has six 1s → mistaken for a flag.

Solution: Sender inserts a 0 after every five consecutive 1s in data. Receiver removes the stuffed 0 to restore original data.

  Original:    0 1 1 1 1 1 1 0   ← six 1s looks like a flag!
  After stuff: 0 1 1 1 1 1 0 1 0 ← extra 0 inserted after five 1s
  Receiver removes stuffed 0 → original data restored ✅
