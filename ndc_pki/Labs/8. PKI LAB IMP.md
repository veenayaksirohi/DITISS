## 1. Objective

Build a complete **3-tier PKI hierarchy** using XCA:

```
Root CA  →  Sub CA  →  User Certificate (Tinku)
```

Then use Tinku's certificate to:

- Digitally sign a **Microsoft Word** document
- Digitally sign a **PDF** document

## 4. Key PKI Terms

| Term                  | Meaning                                                                              |
| --------------------- | ------------------------------------------------------------------------------------ |
| **PKI**               | Public Key Infrastructure — the full system of CAs, certificates, and trust          |
| **CA**                | Certificate Authority — entity that issues and signs certificates                    |
| **Root CA**           | Top-level CA; self-signs its own certificate; highest trust anchor                   |
| **Sub CA**            | Intermediate CA; certified by Root CA; issues end-user certificates                  |
| **CSR**               | Certificate Signing Request — contains public key + identity; sent to CA for signing |
| **Private Key**       | Secret key used for signing; never shared                                            |
| **Public Key**        | Paired with private key; used by others to verify signatures                         |
| **Certificate**       | Binds an identity to a public key; signed by a CA                                    |
| **Certificate Chain** | Trust path: Root CA → Sub CA → User Certificate                                      |
| **Digital Signature** | Cryptographic proof of authenticity and integrity                                    |
| **XBD / XDB**         | XCA database file (stores keys, certs, CSRs)                                         |
| **PEM**               | Base64 text format for certificates and keys                                         |
| **CRT**               | Certificate file (binary or PEM)                                                     |
| **PFX / PKCS#12**     | Bundle: certificate + private key + full chain; used for signing in Word/PDF         |

## 5. Complete PKI Flow

```
┌─────────────────────────────────────┐
│              ROOT CA                │
│         (Self-Signed Cert)          │
│   Signs its own certificate         │
└──────────────────┬──────────────────┘
                   │  Signs Sub CA CSR
                   ▼
┌─────────────────────────────────────┐
│              SUB CA                 │
│     Certified by Root CA            │
│     Signs user certificates         │
└──────────────────┬──────────────────┘
                   │  Signs Tinku's CSR
                   ▼
┌─────────────────────────────────────┐
│         USER CERT (Tinku)           │
│     Certified by Sub CA             │
│     Key Usage: Digital Signature    │
└──────────────────┬──────────────────┘
                   │
         ┌─────────┴──────────┐
         ▼                    ▼
   Word Document          PDF Document
   (Digital Sign)         (Digital Sign)
```

## 6. Part 1 — Create Root CA

### Step 1 — Install XCA

Install XCA from the official source. On first launch, XCA prompts for a database location.

---

### Step 2 — Create Root CA Database

| Field             | Value                         |
| ----------------- | ----------------------------- |
| Folder            | `C:\MyFiles\MyPKI\01-RootCA\` |
| Database filename | `01-01-RootCA_DB.xdb`         |
| Password          | `root@123` (example)          |

> **Why password?** Protects the private keys and certificates stored in the `.xdb` database file.

---

### Step 3 — Create Root CA Private Key

Navigate:

```
XCA → Private Keys tab → New Key
```

| Field     | Value        |
| --------- | ------------ |
| Name      | `RootCA-Key` |
| Algorithm | RSA          |
| Key Size  | 4096 bits    |

Click **Show Details** to verify key generation.

> **Explanation:** The private key is the most critical component. It is used by Root CA to sign all Sub CA certificates. It must never leave the Root CA database.

---

### Step 4 — Create Root CA Certificate

Navigate:

```
XCA → Certificates tab → New Certificate
```

**Template:** Select `Root CA` → Click **Use this Template**

Most fields auto-fill from the template. Verify and modify only where needed:

#### Subject Tab

| Field            | Example Value |
| ---------------- | ------------- |
| CN (Common Name) | `RootCA`      |
| O (Organization) | `ABC Pvt Ltd` |
| OU (Org Unit)    | `Security`    |
| C (Country)      | `IN`          |

#### Extensions Tab

Auto-filled from template. Verify:

```
CA = TRUE
```

> This flag means this certificate can issue (sign) other certificates.

#### Key Usage Tab

Auto-selected:

```
✔ Certificate Sign
✔ CRL Sign
```

> These two usages allow Root CA to sign certificates and maintain a Certificate Revocation List.

#### Advanced / Netscape Tabs

No changes required when using the Root CA template.

#### Signing

Select:

```
Self Signed
```

> **Why Self Signed?** Root CA is the top of the chain — there is no higher authority to sign it. So it signs its own certificate. Issuer = Subject.

---

### Step 5 — Export Root CA Certificate

```
Right-click certificate → Export → PEM/CRT format
```

| Output File     | Location                      |
| --------------- | ----------------------------- |
| `01-RootCA.crt` | `C:\MyFiles\MyPKI\01-RootCA\` |

> This `.crt` file will be needed later by Sub CA and Tinku to build the trust chain.

## 9. Part 4 — Complete Sub CA Setup

Switch back to the **Sub CA XCA instance**.

### Step 1 — Import the Signed Certificate

```
XCA → Certificates tab → Import
```

Import:

```
02-03-SubCA.crt
```

Sub CA now has:

- Its own private key (already in the database)
- Its certificate signed by Root CA

---

### Step 2 — Import Root CA Certificate

Also import the Root CA's certificate into Sub CA's database:

```
Import: 01-RootCA.crt
```

> **Why?** This creates the **certificate chain** inside the Sub CA database.
> Without Root CA's certificate, the chain is incomplete and verification fails.

#### Certificate Chain at this point:

```
Root CA
   └── Sub CA
```

## 12. Part 7 — Import Certificate Chain into Tinku DB

Switch to the **Tinku XCA instance**.

### Import all three certificates:

```
XCA → Certificates tab → Import
```

Import these files one by one:

| File              | Role                               |
| ----------------- | ---------------------------------- |
| `03-03-Tinku.crt` | Tinku's own certificate            |
| `02-03-SubCA.crt` | Sub CA certificate (issuer)        |
| `01-RootCA.crt`   | Root CA certificate (trust anchor) |

#### Complete Certificate Chain Now:

```
Root CA
   └── Sub CA
          └── Tinku
```

> **Why import all three?**
> When Word or Adobe verifies the signature, they walk the chain:
> `Tinku → Sub CA → Root CA`
> If any link is missing, verification fails.

## 13. Part 8 — Export PFX (PKCS#12)

PFX bundles everything needed for digital signing into one file.

```
XCA → Certificates tab → Right-click Tinku cert → Export
```

Choose format:

```
PKCS#12 (.pfx)
```

| Field       | Value                        |
| ----------- | ---------------------------- |
| Output File | `Tinku.pfx`                  |
| Location    | `C:\MyFiles\MyPKI\03-Tinku\` |
| Password    | `user123`                    |

> **What is inside a PFX file?**
>
> | Component           | Purpose          |
> | ------------------- | ---------------- |
> | Tinku's Certificate | Identity         |
> | Tinku's Private Key | Used for signing |
> | Sub CA Certificate  | Chain link       |
> | Root CA Certificate | Trust anchor     |
>
> Applications like Microsoft Word and Adobe Acrobat import this single `.pfx` file to perform digital signing.

## 15. Question 1 — Digitally Sign a Word Document

### Steps

**1.** Open Microsoft Word → Create or open a document.

Example content:

```
Hello,
My name is Tinku.
This document is digitally signed.
```

**2.** Navigate:

```
File → Info → Protect Document → Add a Digital Signature
```

**3.** When prompted, select:

```
Certificate: Tinku
```

(Windows Certificate Store must have Tinku.pfx imported — double-click `.pfx` and follow the wizard if needed.)

**4.** Click **Sign** → Save the document.

**5.** Close and reopen the document.

You should see:

```
✔ Digitally Signed
   Signed by: Tinku
   Certificate: Valid
```

---

### What Word Verifies

| Property            | Explanation                                      |
| ------------------- | ------------------------------------------------ |
| **Integrity**       | Document has not been modified after signing     |
| **Authentication**  | Signed by Tinku (verified via certificate chain) |
| **Non-Repudiation** | Tinku cannot deny having signed the document     |

> **Note:** If the document is edited after signing, Word marks the signature as **Invalid**.

## 17. Viva / Exam Q&A

**Q1. Why is Root CA self-signed?**

Root CA is the highest trust authority — there is no higher CA to sign it. So it signs its own certificate. The issuer and subject fields are identical.

---

**Q2. Why create a Sub CA instead of signing directly from Root CA?**

To keep the Root CA **offline and secure**. If the Root CA is compromised, the entire PKI collapses. The Sub CA handles day-to-day certificate issuance, while Root CA remains protected.

---

**Q3. What is a CSR and what does it contain?**

A Certificate Signing Request contains:

- Applicant's **public key**
- **Identity information** (CN, O, OU, C)

It does **NOT** contain the private key. It is sent to a CA for signing.

---

**Q4. Why export a PFX file instead of just a `.crt`?**

A `.crt` contains only the certificate (public part). A `.pfx` also contains the **private key** and the **certificate chain**. Applications like Word and Adobe need the private key to create digital signatures.

---

**Q5. What happens if a document is modified after signing?**

The document's hash changes. When the signature is verified, the stored hash (inside the signature) does not match the computed hash of the modified document. The application reports: **Signature Invalid — Document has been tampered with.**

---

**Q6. Why import Root CA certificate into Sub CA and Tinku databases?**

To **complete the certificate chain**. When an application verifies Tinku's signature, it must trace the trust path: Tinku → Sub CA → Root CA. If any certificate in the chain is missing, verification fails.

---

**Q7. What is the difference between Key Usage: Digital Signature vs Certificate Sign?**

| Key Usage         | Who uses it               | Purpose                             |
| ----------------- | ------------------------- | ----------------------------------- |
| Digital Signature | End users (Tinku)         | Sign documents, emails, executables |
| Certificate Sign  | CA only (Root CA, Sub CA) | Issue and sign other certificates   |

---

**Q8. What is the correct file naming sequence in this lab?**

| File                  | Stage                     |
| --------------------- | ------------------------- |
| `01-01-RootCA_DB.xdb` | Root CA database          |
| `01-RootCA.crt`       | Root CA certificate       |
| `02-01-SubCA_DB.xdb`  | Sub CA database           |
| `02-02-SubCA.csr`     | Sub CA signing request    |
| `02-03-SubCA.crt`     | Sub CA signed certificate |
| `03-01-Tinku_DB.xdb`  | Tinku database            |
| `03-02-Tinku.csr`     | Tinku signing request     |
| `03-03-Tinku.crt`     | Tinku signed certificate  |
