## 4. Key PKI Terms

| Term                  | Meaning                                                                              |
| --------------------- | ------------------------------------------------------------------------------------ |
| **PKI**               | Public Key Infrastructure — the full system of CAs, certificates, and trust          |
| **CA**                | Certificate Authority — entity that issues and signs certificates                    |
| **Root CA**           | Top-level CA; self-signs its own certificate; highest trust anchor                   |
| **Sub CA**            | Intermediate CA; certified by Root CA; issues end-user certificates                  |
| **CSR**               | Certificate Signing Request — contains public key + identity; sent to CA for signing |
| **Private Key**       | Secret key used for signing; never shared                                            |
| **Public Key**        | Paired with private key; used by others to verify signatures                         |
| **Certificate**       | Binds an identity to a public key; signed by a CA                                    |
| **Certificate Chain** | Trust path: Root CA → Sub CA → User Certificate                                      |
| **Digital Signature** | Cryptographic proof of authenticity and integrity                                    |
| **XDB**               | XCA database file (stores keys, certs, CSRs)                                         |
| **PEM**               | Base64 text format for certificates and keys                                         |
| **CRT**               | Certificate file (binary or PEM)                                                     |
| **PFX / PKCS#12**     | Bundle: certificate + private key + full chain; used for signing in Word/PDF         |

## 5. Complete PKI Flow

```
┌─────────────────────────────────────┐
│              ROOT CA                │
│         (Self-Signed Cert)          │
│   Signs its own certificate         │
└──────────────────┬──────────────────┘
                   │  Signs Sub CA CSR
                   ▼
┌─────────────────────────────────────┐
│              SUB CA                 │
│     Certified by Root CA            │
│     Signs user certificates         │
└──────────────────┬──────────────────┘
                   │  Signs Tinku's CSR
                   ▼
┌─────────────────────────────────────┐
│         USER CERT (Tinku)           │
│     Certified by Sub CA             │
│     Key Usage: Digital Signature    │
└──────────────────┬──────────────────┘
                   │
         ┌─────────┴──────────┐
         ▼                    ▼
   Word Document          PDF Document
   (Digital Sign)         (Digital Sign)
```

### Step 4 — Create Root CA Certificate

Navigate to: `XCA → Certificates tab → New Certificate`

Select template `Root CA` → click **Use this Template**.

#### Subject Tab

| Field            | Value         |
| ---------------- | ------------- |
| CN (Common Name) | `RootCA`      |
| O (Organization) | `ABC Pvt Ltd` |
| OU (Org Unit)    | `Security`    |
| C (Country)      | `IN`          |

#### Extensions Tab

Verify the following is set (auto-filled from template):

```

```

> This flag means this certificate can issue (sign) other certificates.

#### Key Usage Tab

Verify the following are selected (auto-filled from template):

```
✔ Certificate Sign
✔ CRL Sign
```

#### Signing

Select **Self Signed**.

> Root CA is the top of the chain — there is no higher authority to sign it. Issuer = Subject.

Click **OK** to create the Root CA certificate.

### Step 5 — Export Root CA Certificate (CRT)

```
Right-click RootCA certificate → Export → PEM / CRT format
```

| Output File     | Location                      |
| --------------- | ----------------------------- |
| `01-RootCA.crt` | `C:\MyFiles\MyPKI\01-RootCA\` |

> This `.crt` file will be imported into Sub CA and Tinku databases to build the trust chain.

---

### Step 6 — Export Root CA as PFX (PKCS#12)

Exporting Root CA as PFX bundles the **Root CA private key + self-signed certificate** into one encrypted file. This is useful for backup and for restoring the Root CA into another machine or XCA instance.

```
Right-click RootCA certificate → Export → PKCS#12 (.pfx)
```

| Field       | Value                         |
| ----------- | ----------------------------- |
| Output File | `01-RootCA.pfx`               |
| Location    | `C:\MyFiles\MyPKI\01-RootCA\` |
| Password    | `root@123`                    |

> **Why export Root CA as PFX?**
> The `.pfx` includes the **private key** (`RootCA-Key`). Without it, Root CA cannot sign Sub CA certificates on another machine. Keep this file extremely secure — anyone with this PFX and password can impersonate your Root CA.

Contents of `01-RootCA.pfx`:

| Component                | Purpose                          |
| ------------------------ | -------------------------------- |
| Root CA Certificate      | Self-signed identity             |
| RootCA-Key (Private Key) | Used to sign Sub CA certificates |

### Troubleshooting — PFX Option Not Appearing / Only .CRT in Dropdown

**Root cause:** XCA only shows the PKCS#12 (.pfx) export option when the selected certificate has a **matching private key in the same database**. If the key and certificate are in different databases, or if XCA cannot link them, it falls back to exporting only a `.crt` file.

**How to check:**

1. In the **Tinku XCA instance**, go to the **Private Keys** tab and confirm `Tinku-Key` is listed.
2. Go to the **Certificates** tab, right-click the `Tinku` certificate → **Show Details**.
3. Check the **Key** field — it must show `Tinku-Key`, not `no key`.

If it shows `no key`, the certificate is not linked to a key in this database and PFX export will not be offered.

---

#### Fix 1 — Recreate CSR in the Correct Database (Recommended)

This happens when the CSR was created in a different database from where you are trying to export.

1. Open the **Tinku XCA instance** (`03-01-Tinku_DB.xdb`).
2. Confirm `Tinku-Key` exists in the **Private Keys** tab.
3. Delete the existing Tinku CSR and Tinku certificate if present.
4. Create a **new CSR** for Tinku inside this same database (the key `Tinku-Key` will be auto-linked).
5. Export the new CSR as `03-02-Tinku.csr`.
6. Sign it again from the **Sub CA instance**.
7. Import the newly signed `03-03-Tinku.crt` back into this same Tinku DB.
8. Now right-click the Tinku certificate → Export → the **PKCS#12 (.pfx)** option should appear.

---

#### Fix 2 — Export CRT Instead and Change Extension (Will NOT Work for Signing)

Manually renaming a `.crt` file to `.pfx` does **not** produce a valid PFX. Word and Adobe require the private key bundled inside. Always use Fix 1.

---

#### Fix 3 — Merge Key and Certificate via Temporary Database

Use this only if Fix 1 is not possible.

1. Export `Tinku-Key` as PEM from whichever database holds it (`File → Export → PEM`).
2. Create a new temporary XCA database.
3. Import `Tinku-Key` (PEM) into the temporary DB.
4. Import `03-03-Tinku.crt`, `02-03-SubCA.crt`, and `01-RootCA.crt` into the temporary DB.
5. Right-click the Tinku certificate → Export → **PKCS#12 (.pfx)** → set password `user123`.
6. Save as `Tinku.pfx`.

## 17. Viva / Exam Q&A

**Q1. Why is Root CA self-signed?**

Root CA is the highest trust authority — there is no higher CA to sign it. So it signs its own certificate. The issuer and subject fields are identical.

---

**Q2. Why create a Sub CA instead of signing directly from Root CA?**

To keep the Root CA **offline and secure**. If the Root CA is compromised, the entire PKI collapses. The Sub CA handles day-to-day certificate issuance while Root CA remains protected.

---

**Q3. What is a CSR and what does it contain?**

A Certificate Signing Request contains:

- The applicant's **public key**
- **Identity information** (CN, O, OU, C)

It does **not** contain the private key. It is sent to a CA for signing.

---

**Q4. Why export a PFX file instead of just a `.crt`?**

A `.crt` contains only the certificate (public part). A `.pfx` (PKCS#12) also contains the **private key** and the **certificate chain**, encrypted with a password. Applications like Word and Adobe need the private key to create digital signatures.

---

**Q5. What happens if a document is modified after signing?**

The application recomputes a hash of the document and compares it with the hash stored inside the signature. If they differ, it reports: **Signature Invalid — Document has been tampered with.**

---

**Q6. Why import Root CA certificate into Sub CA and Tinku databases?**

To **complete the certificate chain**. When an application verifies Tinku's signature, it must trace the trust path: `Tinku → Sub CA → Root CA`. If any certificate in the chain is missing, verification fails.

---

**Q7. What is the difference between Key Usage: Digital Signature vs Certificate Sign?**

| Key Usage         | Who uses it                | Purpose                             |
| ----------------- | -------------------------- | ----------------------------------- |
| Digital Signature | End users (Tinku)          | Sign documents, emails, executables |
| Certificate Sign  | CAs only (Root CA, Sub CA) | Issue and sign other certificates   |

---

**Q8. Why does XCA show only `.crt` in the export dropdown instead of `.pfx`?**

XCA only offers PKCS#12 (.pfx) export when the selected certificate has a **matching private key in the same database**. If the private key and certificate are in different XCA databases, the key-certificate link is missing and XCA falls back to `.crt` export only. Fix this by recreating the CSR inside the correct database (the one that holds the private key), then re-signing and re-importing the certificate.

---

**Q9. What is the correct file naming sequence in this lab?**

| File                  | Stage                                                        |
| --------------------- | ------------------------------------------------------------ |
| `01-01-RootCA_DB.xdb` | Root CA database                                             |
| `01-RootCA.crt`       | Root CA certificate (public, for chain)                      |
| `01-RootCA.pfx`       | Root CA cert + private key bundle                            |
| `02-01-SubCA_DB.xdb`  | Sub CA database                                              |
| `02-02-SubCA.csr`     | Sub CA signing request                                       |
| `02-03-SubCA.crt`     | Sub CA signed certificate                                    |
| `02-SubCA.pfx`        | Sub CA cert + private key + Root CA chain bundle             |
| `03-01-Tinku_DB.xdb`  | Tinku database                                               |
| `03-02-Tinku.csr`     | Tinku signing request                                        |
| `03-03-Tinku.crt`     | Tinku signed certificate                                     |
| `Tinku.pfx`           | Tinku cert + private key + full chain (for document signing) |
