# Injection in Stored Procedures Notes

## Introduction

Stored Procedures are precompiled SQL statements stored inside a database and executed by applications.

Although stored procedures improve performance and organization, insecure implementation can still lead to SQL Injection vulnerabilities.

Injection in stored procedures is a major database security risk discussed in secure coding and OWASP security practices.

---

# What is a Stored Procedure?

## Definition

A Stored Procedure is a collection of SQL statements stored in the database and executed as a single unit.

---

# Purpose of Stored Procedures

* Reuse SQL code
* Improve performance
* Reduce network traffic
* Centralize business logic
* Improve security (when implemented correctly)

# What is Injection in Stored Procedures?

## Definition

Injection occurs when untrusted input is improperly handled inside stored procedures, allowing attackers to execute malicious SQL commands.

---

# Important Point

❗ Stored procedures are NOT automatically secure.

If developers build dynamic SQL queries inside procedures, SQL Injection becomes possible.

---

# How Injection Happens

## Unsafe Process

1. User provides input
2. Stored procedure concatenates input into SQL query
3. Database executes malicious SQL

# Vulnerable Stored Procedure Example

## Unsafe Procedure

```sql id="4q4c4z"
CREATE PROCEDURE LoginUser
@username VARCHAR(50)
AS
BEGIN
EXEC('SELECT * FROM users 
WHERE username = ''' + @username + '''')
END;
```

---

# Malicious Input

```sql id="dgps69"
' OR '1'='1
```

---

# Executed Query

```sql id="1mg35u"
SELECT * FROM users 
WHERE username='' OR '1'='1'
```

Authentication bypass occurs.

---

# Why Dynamic SQL is Dangerous

## Dynamic SQL

Dynamic SQL creates queries at runtime using string concatenation.

---

## Dangerous Pattern

```sql id="3g40dz"
EXEC('SELECT * FROM users 
WHERE id=' + @id)
```

---

# Risks of Dynamic SQL

* SQL Injection
* Data theft
* Authentication bypass
* Privilege escalation
* Database destruction

# Types of Injection in Stored Procedures

| Type                   | Description                       |
| ---------------------- | --------------------------------- |
| SQL Injection          | Inject malicious SQL              |
| Blind Injection        | Infer information indirectly      |
| Union Injection        | Combine malicious query           |
| Command Injection      | Execute OS commands               |
| Second-Order Injection | Payload stored and later executed |

# 1. SQL Injection in Stored Procedures

## Example

```sql id="6gntnq"
EXEC('SELECT * FROM products 
WHERE name=''' + @name + '''')
```

Attacker input:

```sql id="m0p1d1"

```

# 2. Blind SQL Injection

## Definition

Application hides errors, but attackers infer data using responses or timing.

---

## Time-Based Injection Example

```sql id="vfiv0m"
'; WAITFOR DELAY '00:00:05' --
```

If response delays → injection exists.

# 4. Second-Order Injection

## Definition

Malicious input stored safely initially but executed later in another query.

# Prevention of Stored Procedure Injection

# 1. Parameterized Queries

## Safe Example

```sql id="58n0qv"
CREATE PROCEDURE GetUser
@id INT
AS
BEGIN
SELECT * FROM users 
WHERE id=@id
END;
```

No string concatenation.

---

# 2. Avoid Dynamic SQL

## Unsafe

```sql id="urj8hn"
EXEC('SELECT * FROM users 
WHERE name=''' + @name + '''')
```

---

## Safe

```sql id="36l30t"
SELECT * FROM users 
WHERE name=@name
```

---

# 3. Input Validation

Validate:

* Length
* Data type
* Allowed characters

---

# 4. Least Privilege Principle

Database accounts should:

* Avoid admin privileges
* Access only required tables

---

# 5. Disable Dangerous Features

Disable:

* xp_cmdshell
* Unused procedures
* Debug options

---

# 6. Error Handling

Do not expose database errors to users.

---

# Unsafe Error Example

```text id="h7x6i5"
SQL syntax error near 'OR 1=1'
```

Helps attackers craft payloads.

---

# 7. Logging and Monitoring

Monitor:

* Failed queries
* Suspicious patterns
* Multiple login failures

---

# Secure Stored Procedure Design

| -------------------- | --------------------- |

# Interview Questions and Answers

## 1. What is a stored procedure?

A stored procedure is a precompiled set of SQL statements stored in the database.

---

## 2. Are stored procedures always secure?

No. Dynamic SQL inside procedures can still cause SQL Injection.

---

## 3. What causes injection in stored procedures?

String concatenation and unsafe dynamic SQL.

---

## 4. What is dynamic SQL?

SQL queries generated at runtime.

---

## 5. How can stored procedure injection be prevented?

* Parameterized queries
* Input validation
* Least privilege
* Avoid dynamic SQL

---

## 6. Why is xp_cmdshell dangerous?

It allows execution of operating system commands.
