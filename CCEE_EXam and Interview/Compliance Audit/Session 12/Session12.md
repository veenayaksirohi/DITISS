# Session 13: SSE-CMM (Systems Security Engineering Capability Maturity Model)

**Duration: 2 Theory Hours**

---

# 1. Introduction to SSE-CMM

## Definition

**SSE-CMM (Systems Security Engineering Capability Maturity Model)** is a framework used to assess and improve the security engineering processes of an organization.

It helps organizations:

* Measure security engineering capability
* Improve security practices
* Establish process maturity
* Reduce security risks
* Ensure consistent security implementation

---

## Full Form

**SSE-CMM = Systems Security Engineering Capability Maturity Model**

Developed by:

* International Systems Security Engineering Association (ISSEA)
* National Security Agency (NSA)
* Defense organizations and industry experts

---

# 2. History and Need of SSE-CMM

## History

Before SSE-CMM:

* Organizations focused mainly on product security.
* No standard process existed for measuring security engineering capability.
* Security activities varied widely among organizations.

To solve these issues:

* Research started in the 1990s.
* Inspired by Software CMM.
* SSE-CMM Project launched to create a standard framework.

In **2002**, SSE-CMM became:

### ISO/IEC 21827

Known internationally as:

**ISO/IEC 21827 – Systems Security Engineering Capability Maturity Model**

---

## Need for SSE-CMM

Organizations needed a framework to:

### 1. Improve Security Processes

Ensure security is built systematically.

### 2. Measure Capability

Evaluate how well security activities are performed.

### 3. Reduce Security Risks

Identify weaknesses before exploitation.

### 4. Increase Trust

Demonstrate security competence to customers.

### 5. Standardize Security Engineering

Provide common security practices.

---

## Why Traditional Security Was Not Enough

Traditional approach:

```text
Develop System
      ↓
```

Problems:

* Expensive

SSE-CMM promotes:

# 6. Capability Levels of SSE-CMM

Capability levels measure maturity.

---

## Level 0 – Not Performed

Characteristics:

* Process does not exist.
* Activities are absent.

Example:

No security testing conducted.

---

## Level 1 – Performed Informally

Characteristics:

* Activities performed.
* No standard process.

Example:

Security testing done occasionally.

---

## Level 2 – Planned and Tracked

Characteristics:

* Activities planned.
* Progress monitored.

Example:

Security testing schedule maintained.

---

## Level 3 – Well Defined

Characteristics:

* Documented procedures.
* Standardized process.

Example:

Formal security testing methodology.

---

## Level 4 – Quantitatively Controlled

Characteristics:

* Metrics collected.
* Performance measured.

Example:

Track vulnerabilities found per release.

---

## Level 5 – Continuously Improving

Characteristics:

* Continuous optimization.
* Lessons learned incorporated.

Example:

Automated security improvements.

---

## Capability Level Diagram

```text
Level 5 → Continuously Improving

Level 4 → Quantitatively Controlled

Level 3 → Well Defined

Level 2 → Planned & Tracked

Level 1 → Performed Informally

Level 0 → Not Performed
```
